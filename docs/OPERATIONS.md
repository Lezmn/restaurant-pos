# คู่มือดูแลระบบ (สำหรับเจ้าของร้าน / คนดูแลเครื่อง)

คำสั่งทั้งหมดรันที่โฟลเดอร์ราก repo บนเครื่องที่ deploy — ย่อ `docker compose -f docker-compose.prod.yml` เป็น `dc`

```bash
alias dc='docker compose -f docker-compose.prod.yml'
```

## สำรองและกู้ข้อมูล

**อัตโนมัติ:** service `backup` สำรองทุกวันตอน `BACKUP_HOUR` (ค่าเริ่มต้น 03:00) ไว้ที่ `./backups/restaurant_db_YYYY-MM-DD_HHMM.dump`
เก็บ `BACKUP_KEEP_DAYS` วัน (ค่าเริ่มต้น 14) เก่ากว่านั้นลบเอง

```bash
dc logs backup --tail 20        # ดูว่าสำรองสำเร็จทุกวัน ("ok" + ขนาดไฟล์)
dc run --rm backup once         # สำรองเองทันที — ทำก่อนอัปเดตระบบ / แก้ข้อมูลใหญ่ทุกครั้ง
```

**ต้องคัดลอกออกนอกเครื่องด้วย** — ไฟล์สำรองอยู่เครื่องเดียวกับฐานข้อมูล ถ้าเครื่องพัง/ถูกขโมย หายพร้อมกัน
เช่น ตั้ง cron ทุกวัน 04:00 ส่งเข้า Google Drive / S3 ด้วย `rclone`:

```bash
0 4 * * * rclone copy /path/to/restaurant-pos/backups remote:restaurant-backups --max-age 48h
```

**กู้ข้อมูล** (ทับข้อมูลปัจจุบันทั้งหมด — สคริปต์จะหยุด API ระหว่างกู้และถามยืนยัน):

```bash
sh deploy/restore.sh backups/restaurant_db_2026-10-22_0300.dump
```

ควรซ้อมกู้ข้อมูลลงฐานข้อมูลทดสอบอย่างน้อยเดือนละครั้ง ไฟล์สำรองที่ไม่เคยลองกู้ = ไม่รู้ว่าใช้ได้จริงไหม

## การเฝ้าระวังระบบ

`GET https://API_DOMAIN/health` ตอบ `200 {"status":"ok","db":"ok"}` เมื่อ API และฐานข้อมูลพร้อม, `503` เมื่อฐานข้อมูลล่ม

- ตั้ง uptime monitor ภายนอก (เช่น UptimeRobot / Better Stack แบบฟรี) ยิง URL นี้ทุก 1–5 นาที
  แจ้งเตือนเข้า LINE / อีเมล / SMS ของเจ้าของร้าน
- endpoint นี้ไม่ต้อง login และไม่นับ rate limit
- ใน Docker: `dc ps` ดูคอลัมน์ STATUS ของ api ต้องเป็น `(healthy)`

```bash
dc ps                      # สถานะทุก service
dc logs api --tail 100     # log ของ API
dc restart api             # รีสตาร์ท API (ออเดอร์ที่บันทึกแล้วไม่หาย)
```

## แผนสำรองเมื่อระบบใช้ไม่ได้ (เน็ตดับ / เครื่องล่ม)

ระบบต้องใช้เน็ต (ลูกค้าสั่งผ่านมือถือ, แท็บเล็ตคุยกับ API) — เตรียมไว้ล่วงหน้า:

1. **กระดาษสั่งอาหาร + ปากกา** ที่หน้าร้านและครัว (ช่อง: โต๊ะ / เมนู / ตัวเลือก / จำนวน / เวลา)
2. **รับเงินสดเป็นหลัก** — PromptPay ใช้ได้ถ้ามือถือลูกค้ายังมีเน็ต ให้เก็บรูปสลิปไว้
3. **ป้าย "ขออภัย ระบบสั่งผ่าน QR ขัดข้อง กรุณาสั่งกับพนักงาน"** วางที่โต๊ะ
4. เมื่อระบบกลับมา: กรอกออเดอร์ย้อนหลังผ่านหน้า **Order** และรับเงินผ่านหน้า **Check** ตามกระดาษ
   แล้วตรวจยอดตอน **ปิดยอดลิ้นชัก** ให้ตรงกับเงินสดจริง
5. เน็ตร้านดับบ่อย → พิจารณา router ที่มี 4G สำรอง

ซ้อมสถานการณ์นี้กับพนักงานสักครั้งก่อนเปิดใช้จริง

## บัญชีผู้ใช้ (บัญชีกลางตามตำแหน่ง)

ร้านใช้ **1 บัญชีต่อตำแหน่ง** (เช่น `kitchen` ทั้งครัว, `cashier` ทั้งหน้าร้าน) ไม่ใช่บัญชีต่อคน

| สถานการณ์ | ทำอย่างไร |
|---|---|
| ส่งมอบระบบให้เจ้าของร้าน | สร้าง ADMIN ด้วยรหัสชั่วคราว (`seed:prod`) → เจ้าของร้าน login แล้วระบบบังคับตั้งรหัสใหม่ทันที บอกรหัสชั่วคราวคนละช่องทางกับชื่อผู้ใช้ |
| มีพนักงานลาออก | หน้า **บัญชีผู้ใช้** → บัญชีของตำแหน่งนั้น → **ตั้งรหัสผ่านใหม่** (ติ๊ก "ออกจากระบบทุกเครื่อง" ไว้) → แท็บเล็ตของร้าน login ใหม่ด้วยรหัสใหม่ |
| แท็บเล็ตหาย | เหมือนพนักงานลาออก — ตั้งรหัสใหม่ + ออกจากระบบทุกเครื่อง |
| เลิกใช้ตำแหน่งนั้นทั้งตำแหน่ง | **ปิดใช้งาน** (ทุกเครื่องหลุดทันที ประวัติยังอยู่ครบ) — ไม่ต้องลบ |
| เจ้าของร้านลืมรหัส | ให้ ADMIN อีกคนตั้งรหัสใหม่ให้ (ควรมี ADMIN อย่างน้อย 2 บัญชี เช่น เจ้าของ + ผู้จัดการ) |
| ADMIN ทุกคนลืมรหัส | คนดูแลเครื่องสร้าง ADMIN ใหม่ผ่านฐานข้อมูล — ระบบไม่มี "ลืมรหัสผ่าน" ทางอีเมล |

- เปลี่ยนรหัสของตัวเองได้เฉพาะ ADMIN (ปุ่มที่หัวจอ) — บัญชีกลางเปลี่ยนเองไม่ได้ กันคนเดียวล็อกทั้งตำแหน่ง
- ร้านต้องมี ADMIN ที่ใช้งานได้อย่างน้อย 1 คนเสมอ ระบบไม่ยอมให้ลบ/ลดสิทธิ์/ปิดคนสุดท้าย
- บัญชีกลางทำให้ประวัติ (ปิดยอด, void บิล) บอกได้แค่ตำแหน่ง ไม่รู้ว่าเป็นใคร

## สต็อกวัตถุดิบ (ถ้าใช้)

- แท็บ **วัตถุดิบ** → **ตั้งยอด** ทุกเช้า (เฉพาะของที่นับจำนวนได้ เช่น ไข่ กุ้ง) ที่เหลือปล่อย "ไม่นับสต็อก" ใช้สวิตช์เปิด/ปิดเหมือนเดิม
- ออเดอร์ตัดยอดเอง เหลือ 0 ปิดเอง ยกเลิกออเดอร์ที่ครัวยังไม่ทำจะคืนยอดให้
- ของเสีย/หกหล่น ต้องตั้งยอดใหม่เอง ไม่งั้นยอดในระบบจะมากกว่าของจริง
